# Transactional configuration reload

SeasonalWeather owns configuration reload in the controller. A reload request creates a durable `config.reload` command, captures exact configuration bytes in a service-owned immutable candidate store, and runs the accepted compiler and staged validator through the durable `config.validate` job contract. The controller independently verifies the candidate identity and report before it can prepare or commit anything.

## Trust and identities

Candidate capture is part of durable command admission, before asynchronous validation starts. The command payload, request identity, and journal bind the immutable candidate reference, exact source SHA-256 and byte length, source-manifest digest, P1-14 candidate SHA-256, and complete candidate-input identity. Execution and restart recovery load that captured reference and never recapture whatever bytes later occupy the configured path. Candidate metadata also binds the selected schema, source and origin manifests, and keyed opaque environment-input identities. Raw environment values are never persisted. Candidate directories and files use restrictive permissions, exclusive creation, no-follow reads, size bounds, collision checks, and verification before report admission. Full candidate compilation, complete-input verification, report loading and digest verification, deterministic diff reconstruction, policy/freshness/acknowledgment checks, and full external report verification finish before quiescent safe-point acquisition. Immediately after acquisition, the held commit fence performs only bounded reads of the admitted candidate metadata/source bytes and stored report bytes, plus the volatile generation, identity, environment, freshness, acknowledgment, plan, cancellation, and lifecycle checks; it does not recompile YAML or rerun complete external verification.

The immutable validation report has its own canonical SHA-256 and active-generation context. Reports may be reused for warning acknowledgment for at most 300 seconds from the trusted validator completion timestamp, with at most 5 seconds of bounded clock skew. Internal validation duration is not report age. Freshness is checked when the stored acknowledged report is loaded, at controller admission, and again under final commit serialization; expiry requires a fresh validation and cannot prepare or commit from the old report. The controller recomputes a deterministic typed diff and binds it to the active generation and identity, candidate identity, report digest, and reload-policy version. Secret entries expose only redacted presence/change metadata. Rendered endpoint values discard URL userinfo, query strings, and fragments. Source text, endpoint credentials/tokens, and secret values are excluded from commands, jobs, SQLite journals, logs, API responses, and diagnostics.

Warnings require an exact acknowledgment containing the source and complete candidate identities, report digest, active generation, sorted warning identities, actor context, trusted validator completion and expiry timestamps, approved age/skew policy, acknowledgment timestamp, and schema version. An `acknowledgment_required` durable command result exposes that bounded nonsecret challenge directly; an authorized caller can submit it unchanged. Generic or wildcard acknowledgment is invalid. Reusing the exact candidate and report is permitted only while all fences and freshness checks remain unchanged.

## Reload policy

Every leaf in the current typed schema and every compiler-declared environment input has an explicit reviewed policy entry. Import and test checks require exact equality between declared and authoritative leaf-pattern sets. Unknown paths and newly introduced leaves without a policy entry fail closed.

- `live`: the currently proven nonstructural deduplication threshold adapter.
- `quiescent`: station and display metadata, cycle and observation settings, alert policies, SAME/CAP/IPAWS/test policy, TTS and audio profiles, service-area settings, and NWWS allowed-WFO targeting.
- `restart_required`: all remaining current paths, including environment-provided secrets, API binding/authentication, database and durable-job paths, persistent directories, external endpoints without a proven reopen adapter, and process/runtime topology.

The most restrictive changed path controls the whole candidate. A mixed `restart_required` candidate is report-only; no live subset is applied. Source-only and effective no-op candidates are audited without changing generation.

## Preparation, safe points, and commit

An immutable resource plan is derived from the trusted diff before active mutation. The sole current live adapter changes only the active configuration/generation fence and deduplication threshold; it does not replace or retarget TTS, timezone, cycle builder, SAME targeting, audio origination, refresher, conductor, or station-publication references. Those replacements require a quiescent plan and a held safe point. A plan whose required disposition differs from the classified diff fails closed.

Quiescent changes wait for an explicit safe point covering alert origination, TTS synthesis, artifact publication, worker-result promotion, segment refresh, conductor mutation, and lifecycle drain state. The real artifact acceptance and result-promotion composition enter the shared activity registry, so in-flight work drains and new work waits behind the held commit gate. Alert admission has priority. A bounded timeout defers the attempt and preserves the old generation.

The commit lock is acquired before the final fence checks. Lock order is reload serialization, optional safe-point gate, bounded candidate/report byte-integrity and volatile fences, durable intent, in-memory reference swap, then the short durable compare-and-swap that increments the generation. The old configuration remains authoritative before this boundary. One successful effective commit increments the generation exactly once; stale concurrent work is rejected.

Precommit activation failures restore captured references in reverse order. Rollback continues reverse cleanup where safe; a rollback exception never replaces the timeout, cancellation, rejection, preparation, or commit failure that triggered it. Both failures are retained as bounded audit evidence, and rollback failure promotes the stable reconciliation diagnostic. Task cancellation remains native `asyncio.CancelledError`; durable cancellation is checked throughout validation, report-only outcomes, preparation, safe-point acquisition, and immediately before commit. Evidence after a reference swap but before durable completion is marked `reconciliation_required`, never success. Old resources retire only after durable commit. Retirement failure leaves the new generation active and records pending cleanup. Jobs, result acceptance, and artifact promotion retain their admitted configuration-generation fences.

## Commands, API, and CLI

`POST /v1/config/reload` accepts only bounded intent fields, an optional expected generation, a bounded safe-point timeout, and exact acknowledgment material. It requires the normal authenticated `control:config` route policy and idempotency key and returns `202` with the durable command identity. Raw YAML, source paths, secret replacements, and unknown fields are rejected. The endpoint is unavailable unless both the controller database and durable job scheduler are enabled.

`seasonalweather config reload --dry-run [PATH]` is a local operator-only comparison. It uses the same candidate store, validator, policy, and redacted diff, but never prepares resources, waits for a safe point, retires resources, or changes generation. JSON output is stable and suitable for automation.

## Audit and recovery

The operational SQLite database owns the active-generation record and narrow reload-attempt journal; the accepted command and job repositories remain authoritative for generic state. Audits contain bounded command/idempotency identities, actor/authorization context, normalized reason, request/start/completion timing, old/candidate/report/diff/validator-stamp/policy identities, grouped paths, warning identities and acknowledgment, the exact successful or timed-out safe-point snapshot and wait, preparation/activation/rollback/retirement/reconciliation states, diagnostic codes, and final generation. They contain no raw source, secrets, headers, environment dumps, URL credentials/query tokens, or arbitrary exception strings.

Important outcomes are `noop`, `dry_run`, `restart_required`, `acknowledgment_required`, `deferred`, `cancelled`, `rolled_back`, `reconciliation_required`, and `committed`. On every startup, reconstruction activates the explicit durable target generation—not an inferred increment—and synchronizes active service state, orchestrator state, job-admission fences, and the durable row to that exact value, even when the configured and durable candidate identities already match. Terminal reload evidence repairs a lost generic command acknowledgment according to the exact outcome. Repair selects only attempts whose generic command still needs finalization, so unrelated historical terminal attempts do not consume the bounded batch. Unfinished retirement/reconciliation work is not treated as terminal evidence. Ambiguous journal evidence is reconciled against the durable active generation and complete identities; no single file or memory reference proves success.

Stable reload diagnostics are `SWCFG0004`, `SWCFG2005`, `SWCFG3003`, `SWCFG4003`, `SWCFG7008`, and `SWCFG8001`. Ordinary validation findings retain their P1-14 codes.

Phase 1 validation executes in deterministic embedded scaffolding through the durable job repository. Real worker execution and transport, backend-neutral or remote TTS, NWWS redesign, segment registries, general configuration/diagnostic catalog HTTP APIs, deployment changes, PostgreSQL, PostGIS, and Redis remain deferred.
