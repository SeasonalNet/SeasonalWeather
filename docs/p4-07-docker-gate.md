# P4-07 disposable Docker gate

From a developer checkout, use a Docker context with permission to create containers, networks and volumes:

```bash
make phase4-docker-gate
```

The harness builds and loads missing controller and routine-worker images using the repository's provenance-aware build interface. For automatic builds, set up the repository `.venv` or point `PYTHON` at an equivalent environment. Existing image tags are reused; to refresh them after checkout changes, use `make images`. Avoid invoking raw Bake without build metadata: the image compatibility checks require a matching software version.

The runner needs Bash, GNU `timeout`, Docker Compose and access to fetch the repository's Icecast and Liquidsoap images and `postgis/postgis:17-3.5` if they are not already cached. Docker must be able to run that image on the developer host. The runner verifies public PostGIS SRID 4326 and configures a dedicated, owned archive schema before starting the controller. It reuses `compose.yaml`, `config/config.yaml` and the production Liquidsoap script, with a private project name and disposable dummy configuration. The stack uses an internal network; the base Compose Icecast port is restricted to a dynamically allocated IPv4 loopback port. No host configuration, live secrets, existing volumes or systemd units are used. Do not use a production Docker context.

A pass requires the controller and worker to become ready, the archive migration to exist in real PostgreSQL, and Icecast to return decoded audio before, during and after a PostgreSQL stop. At each checkpoint the gate starts one continuous FFmpeg listener on the MP3 mount (the Ogg mount can start a new logical stream at track metadata changes) and submits one quiet synthetic WAV directly to Liquidsoap's voice plane. The marker contains no alert message or alert signaling. The voice plane has priority over routine audio, so the probe does not depend on the routine queue draining. No queue is flushed; silence or a tone from an earlier checkpoint cannot pass. While PostgreSQL is stopped, the runner writes the empty P4-04 snapshot fixture through the application's outbox helper. The runner also restarts the controller while PostgreSQL is still stopped, checks controller and worker readiness and the stream again, and confirms the snapshot remains pending. After PostgreSQL restarts it verifies the same UUID and payload in PostgreSQL with non-broadcastable `local_outbox_replay` provenance and verifies that SQLite acknowledged that UUID by removing it. Controller readiness and container start timestamps check that the initial outage and subsequent PostgreSQL recovery did not trigger unplanned restarts.

The gate then reruns the production safe migration runner on the retained schema and checks that no versions were applied and that migration history is unchanged. A deterministic forecast response goes through bounded recovery and the real PostgreSQL repository; the gate verifies the checkpoint links to the expected archive row and both are non-broadcastable. It uses `pg_dump` and `pg_restore` inside the PostgreSQL container to restore into a separate disposable database, then checks migration history, the replayed outage snapshot, the recovered row and checkpoint, and PostGIS SRID 4326. This tests a logical backup of PostgreSQL, not recovery of controller volumes or live NWS ingress.

The gate also requires a non-placeholder station ID WAV committed through the controller-to-worker synthesis path on a fresh database. The listener probe separately checks sampled output using an injected marker; it does not verify routine queue progress, that the station ID itself aired, gap-free playback, weather ingress, alert generation, or upstream backfill. It tests replay of an injected outbox fixture, not the path that originates alerts. No real weather alert is transmitted.

The runner prints per-stage evidence and exits nonzero on failure. It prints Compose status and bounded service log tails before failure teardown. An exit, interrupt or termination triggers `down --volumes --remove-orphans` scoped to the generated project. A failed teardown reports the project name and retains the dummy config so the same scoped teardown can be retried. A forced kill or daemon failure can leave resources behind; identify them by their exact `com.docker.compose.project` label and remove only that disposable project's resources.
